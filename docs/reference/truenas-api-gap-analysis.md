# TrueNAS API Gap Analysis for scale-csi

> Source of truth: `docs/reference/truenas-api-methods.json`, live `core.get_methods` from TrueNAS `26.0.0-BETA.2`. Driver evidence: `pkg/truenas/*.go`. Counts below are method names, not call-site counts.

## Technical summary

- The client resolves **88 distinct method names**: **87 exist in the 26.0 dump** and **1 (`service.reload`) does not**. The code falls back to the available `service.control` method.
- Snapshot lifecycle coverage is already complete for `pool.snapshot` (10/10). The main gaps are scheduled/remote data protection, backend health signals, attachment/process safety checks, and more efficient job orchestration.
- TrueNAS 26.0 exposes `zfs.resource.*` and `zfs.resource.snapshot.*` path-scoped APIs. The driver uses `zfs.resource.query` plus four snapshot-resource methods, while retaining `pool.dataset.*`/`pool.snapshot.*` for lifecycle operations the resource surface does not replace.
- The dump marks `pool.scrub.run` and `pool.scrub.scrub` deprecated in 26.0 and directs callers to the new job method `zpool.scrub.run`.
- This is a capability inventory, not an implementation recommendation. Every description, type, default, job flag, and role comes from the dump; every “currently passed” claim comes from Go call sites and their serialized structs/maps.

## Top 10 highest-value unexploited capabilities

| Rank | Capability | API evidence | scale-csi value |
| ---: | --- | --- | --- |
| 1 | Persistent remote replication | `replication.create`, `replication.run`, `replication.restore` | Adds scheduled remote ZFS DR and restore; the driver only runs a local one-time copy. |
| 2 | Job waiting without polling | `core.job_wait` | Accepts a job ID to wait for completion; the driver currently polls `core.get_jobs`. |
| 3 | Bulk RPC dispatch | `core.bulk` | Sequentially runs one method over multiple parameter sets and returns per-call results; callers must inspect each result even when the bulk job succeeds. |
| 4 | Pool scrub state and control | `pool.scrub.query`, `zpool.scrub.run` | Exposes scrub state plus the 26.0 job-backed execution method; the older pool execution methods are deprecated. |
| 5 | Appliance alert ingestion | `alert.list` | Returns active and dismissed alerts for storage-health observability. |
| 6 | Dataset attachment/process checks | `pool.dataset.attachments`, `pool.dataset.processes` | Identifies service attachments and processes before lifecycle actions. |
| 7 | Efficient snapshot counts | `zfs.resource.snapshot.count`, `pool.dataset.snapshot_count` | Counts snapshots without materializing full snapshot lists. |
| 8 | Disk thermal telemetry | `disk.temperatures`, `disk.temperature_agg` | Adds hardware temperature signals beyond the currently used alert-threshold lookup. |
| 9 | Replication impact previews | `replication.target_unmatched_snapshots`, `replication.count_eligible_manual_snapshots` | Previews source/target snapshot effects before a DR run. |
| 10 | Snapshot-task retention impact | `pool.snapshottask.update_will_change_retention_for`, `delete_will_change_retention_for` | Reports which snapshots would have retention changed before task mutation/deletion. |

- **Ignored** means the 26.0 schema accepts the knob but the current Go wrapper/call sites do not send or expose it. It does not mean the knob should be adopted.
- `omitempty` fields are listed as passable by the client even though zero values are omitted on a particular request.
- All standard filterable query methods accept these shared query-options. Rows below name the subset used and list the remainder as ignored.

### 26.0 schema incompatibilities visible in the Go surface

- `service.reload` is absent. The client probes it and then uses `service.control("RELOAD", service, {})`.
- `DatasetCreateParams` can serialize four fields absent from both live 26.0 `pool.dataset.create` variants: `logbias`, `primarycache`, `secondarycache`, and `xattr`. The Go 26.0 key-scope gate rejects the first three, but currently classifies `xattr` as filesystem-valid; the dump provides no 26.0 schema path for it.
- Existing-snapshot property mutation is not a viable 26.0 path in the driver: no `zfs.resource.snapshot.update` method exists, and the Go code records that `pool.snapshot.update` silently drops such writes on 26.0. Snapshot properties are therefore applied during `pool.snapshot.create`.

## Limits and validation notes

- The dump is a point-in-time contract for TrueNAS 26.0.0-BETA.2; it does not prove behavior on the driver's older supported TrueNAS releases.
- Where a method or field description is empty, the tables say `Schema description is empty.` No behavior was inferred to fill the gap.
- Role arrays are the schema's allowed role groups, not a claim that every listed role is required simultaneously. `roles: []` is rendered as `None listed`; this does not infer that authentication or authorization is unnecessary.
- Candidate ranking uses only capabilities stated in method/parameter descriptions and current driver behavior. It does not estimate implementation effort or operational safety.

## Development decisions supported by this inventory

1. Prefer the 26.0 `zfs.resource.*` read/count paths where their schema directly covers the needed projection; retain `pool.*` lifecycle calls where the resource family has no equivalent or the driver relies on documented behavior.
2. Treat `service.reload` as a compatibility probe, not a 26.0 API dependency.
3. Evaluate `core.job_wait` before adding more polling loops and `core.bulk` before adding N-per-object reconciliation calls.
4. If storage health is added to CSI `VolumeCondition`, start with read-only `pool.query`/`pool.scrub.query`, `alert.list`, and disk temperature methods; their schemas expose the needed state without authorizing maintenance mutations.
5. Keep remote replication/cloud sync opt-in and separate from baseline volume lifecycle: their schemas expose credentials, retention, schedules, and job-backed side effects beyond CSI create/delete semantics.
